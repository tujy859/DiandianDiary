# 项目开发、架构与体验审计（2026-10-17）

审计基线：`main` / `4a55299`。开始时工作目录干净；未切换或修改其他 worktree。根目录没有 `.codegraph/`，按协作规则直接核查源码。本文记录发现，不表示问题已修复。

## 总体判断

项目的基本方向合理：单个业务云函数、单个 agent、工具提供事实、用户确认后保存日记、服务端家庭鉴权和版本校验，都与小型家庭宠物记录产品相称。没有证据支持改成微服务、多 agent、事件总线或全面状态管理框架。

当前主要问题是状态生命周期不完整，部分局部保护没有组成端到端闭环；同时，聊天页面承担过多职责，历史兼容代码和维护文档仍混有旧设计。建议先解决数据丢失和覆盖，再局部拆分，最后做体验减法。

## 已确认缺陷

### A1 · P1：切换话题后，同一设备的待确认照片也无法恢复

- 位置：`utils/chat-store.ts:37`、`:169`；`pages/chat/chat.ts:375`、`:470`。
- 当前本机缓存仅按账号、家庭、宠物保存一个话题。云端同步过滤未保存日记的本机照片；开始新话题会覆盖本机当前槽位，打开旧话题只从云端恢复。
- 触发：发送照片、生成待确认卡，不保存，开新话题，再打开旧话题。30 分钟自动换话题也走同一路径。
- 隔离复现：调用真实 `pushSession → saveLocalSession(newSession) → openSession`，云调用替换为内存文档；重新打开后用户消息 `photos=[]`，卡片 `photos=[]`，状态仍为 `pending`。纯照片草稿因此失去可保存内容。文件可能仍在本机，但界面已失去引用。
- 这超出“未保存照片不能跨设备出现”的已知边界，同一设备也受影响。
- 建议：按稳定话题标识保存未完成草稿和本机照片引用，恢复时合并；先确保有本机恢复路径，再考虑清理。不要为解决此问题擅自改成确认前上传照片。

### A2 · P1：同步冲突后的本机消息会被下一次拉取覆盖

- 位置：`utils/chat-store.ts:152`；`pages/chat/chat.ts:273`、`:393`。
- `pullSession` 注释声称保留未同步内容，但实现只比较云端版本。`syncSession` 失败后仅弹提示，最终仍将 `_syncPending` 减为零，没有持久化 dirty / failed 状态。
- 触发：两台设备打开同一话题，另一台先提交；本机追加消息提交冲突。之后切回聊天页，`syncSessions` 会接受较新云端版本并保存到本机槽位。
- 隔离复现：本机 v1 包含独有消息，云端 v2 不包含该消息；真实 `pullSession` 返回值中独有消息消失。页面随后明确调用 `saveLocalSession`，会将这个结果落盘。
- 提示“本机内容已保留”只描述失败瞬间，不能保证后续恢复；同一话题目录项还会因 id 相同直接关闭，不能依靠提示中的“重新打开”解决冲突。
- 建议：持久化未同步标记与本机快照；拉取不能覆盖 dirty 话题。允许显式选择云端版、保留为新话题或重试，不必立即实现自动复杂合并。

### A3 · P1：编辑表单没有绑定读取时版本，可能静默覆盖他人更新

- 位置：`pages/diary/diary.ts:104`；`utils/repository.ts:254`；宠物表单同类问题见 `pages/mine/mine.ts:79`、`utils/repository.ts:220`。
- 表单保存的是文字、日期、照片等字段，没有保存编辑开始时的 version。repository 提交时重新从当前缓存读取 version。
- 触发：用户基于 v1 打开编辑，另一设备写入 v2；页面恢复或后台刷新将缓存更新为 v2，但旧编辑表单仍在。提交旧表单时携带 v2，服务端版本检查通过，覆盖另一设备内容。
- 隔离复现：保留 v1 编辑内容，将真实 store 缓存替换为 v2，再调用真实 `updateRecord`；捕获请求为 `version: 2`，正文却是基于 v1 的编辑内容。服务端无法据此识别冲突。
- 建议：打开编辑时冻结记录 id、version 和表单基线，提交显式传 expectedVersion；冲突保留用户表单并提供刷新/重开选择。宠物编辑应采用同一契约。

### A4 · P2：“清除本机缓存”没有清除实际聊天缓存

- 位置：`utils/store.ts:278`；`utils/chat-store.ts:37`；`pages/mine/mine.ts:217`。
- `clearAll` 清理旧的 `jd_messages_*`，而当前会话在 `jd_chat_<user>_<family>_<pet>`。界面承诺清除缓存和聊天，但实际聊天键保留。
- 隔离复现：使用真实 store 和 chat-store 保存会话、调用 `clearAll`，`loadLocalSession` 仍返回原会话。宠物缓存重新拉取后可再次读到它。
- 建议：统一当前家庭的缓存清理入口，明确覆盖现用聊天键，并使进行中的旧同步失效，避免清理后又回写。此发现不意味着退出登录也存在同一问题：`family-state.ts` 的退出清理已覆盖 chat 前缀。

## 架构与长期维护风险

### A5 · P2：全量刷新与照片解析绑定，成本及失败范围随历史增长

- 位置：`utils/repository.ts:102–132`；`pages/album/album.ts:90`。
- 每次实际刷新依次读取所有宠物、所有日记，再以每批 9 个解析所有照片链接，最后一次性替换整个缓存。时光册同时构造全部时间轴和画廊数据；读取单条详情也使用全量刷新。
- 例：一个宠物有 1000 条日记、每条一张独立照片时，当前循环至少需要 101 次日记分页请求（包括末尾空页）和 112 次照片链接请求，另有身份和宠物读取。它们主要串行执行；这是代码推算，不是线上压测结果。
- 任一照片解析批次失败会阻止本轮整个快照提交。`mediaMap` 还会保留每次出现的签名 URL 到 fileId 的反向映射，没有过期淘汰；是否增长取决于服务端是否返回新链接。
- 文档已承认小规模边界，因此不把它描述成新发现的线上故障。但产品目标是长期积累回忆，需要明确容量验收。
- 建议：先拆开文字读取与图片链接失败处理，详情用现有 `diary.get`，时光册按需分页与解析可见照片；给反向映射设生命周期。事实查询目前依赖全量本机记录，分页改造时必须同时保证查询不会把“已加载部分”冒充全部。

### A6 · P2：聊天页的状态编排过度集中，兼容实现没有清晰退场边界

- `pages/chat/chat.ts` 当前 1201 行，同时负责键盘、页面生命周期、会话目录/同步、模型工具与 JSON 降级、草稿更正/保存、照片处理、开发流程测试与日志。长度不是缺陷证据，但 A1/A2 显示这些职责之间存在遗漏。
- `store.ts` 仍暴露旧本机宠物/日记写接口、旧消息迁移和旧头像实现，而正式写入走 repository，头像走 `pet-avatars.ts`。不能直接删除：测试和历史兼容可能依赖；应先核对调用者，再移到明确的测试/兼容边界。
- 全部家庭写操作更新同一家庭 revision，包括会话同步与照片登记。这样可以与移除成员的事务竞争，具有实际安全目的；代价是共享写热点。小家庭阶段先测量冲突率，不为理论扩展性撤掉鉴权保护。
- 建议仅抽离会话生命周期、草稿保存协调、视口键盘处理三个具体职责，并集中管理它们的状态归属。保留单云函数和现有纯逻辑工具，不引入通用编排框架。
- 日期证据校验、幂等请求、取消代次、服务端授权不能因为“代码多”就删掉；它们直接保护用户事实和数据。

## 用户体验取舍与文档问题

### A7 · P2：权限限制直到提交后才告知

- 位置：`pages/diary/diary.wxml:47` 的 actions、`pages/mine/mine.ts:79`；服务端约束见 `cloudfunctions/diaryApi/service.js:312`、`:343`。
- 日记详情对所有可读记录显示编辑/删除，宠物页对成员提供管理表单；但普通成员不能编辑他人日记或管理宠物。用户可能填完表单甚至处理照片后才收到拒绝。
- 建议把可编辑能力带到页面，禁用或隐藏不适用动作，并说明创建者/作者限制；服务端鉴权继续保留。属于源码确认的交互路径，尚未双账号真机复现。

### A8 · 产品取舍：模型配置成为浏览已有回忆的前置条件

- 位置：`utils/onboard.ts:10–27`，时光册与我的调用同一个 `guardReady`。
- 换设备尚未配置模型时，即使已登录家庭，也无法直接浏览时光册或管理宠物。对开发者自用工具可以接受，对普通养宠用户首次体验门槛偏高。
- 这符合当前已明确的产品约定，不作为违背需求的代码 bug，也不在审计中擅自改动。若目标转为普通用户，建议讨论将登录/家庭守卫与模型能力守卫拆开，模型前置仅用于生成操作。
- 30 分钟自动换话题同样需要用户验证；优先解决 A1，再判断是否应改为提示而非自动切换。不要一边自动收尾，一边让用户失去待确认照片。

### A9 · P1（文档准确性）：聊天与未确认草稿的上云说明与实现相反

- `docs/cloud-backend.md:82` 明确写“普通聊天、未确认草稿……不上传到此后端”；`:176` 又称聊天继续保存在本机。
- 实际 `pages/chat/chat.ts:900` 的 persist 立即同步，`utils/chat-store.ts:174–195` 上传消息文本和草稿，`cloudfunctions/diaryApi/service.js:392` 将它们写入 `chat_sessions`。过滤的是尚未入库的本机照片，不是聊天文字或草稿文字。会话按用户隔离，不能由此推断其他家庭成员可以读取私人聊天。
- 建议直接修正专题正文的数据流，区分个人云端会话、家庭共享日记、本机未保存照片、设备级模型配置；核对产品中的数据用途说明。此处优先级针对错误的数据边界承诺，不是已确认的数据泄露。

### A10 · P2：当前能力和运维说明仍混有历史残留

- README“当前功能”和目录表仍列出本机旧数据导入，但当前 family 页面与 repository 已无对应入口/实现；云开发正文仍提供返回本机模式、导入操作步骤。
- 云开发接口表未列 session 接口；索引章节称其他业务都按文档 ID 读取，而 `session.list` 使用 familyId / petId / userId / deletedAt 条件和 `_id` 排序。应补充真实查询与索引核查说明；未查询云环境，不能据此断言线上缺索引或一定报错。
- 开发记录顶部“当前状态”仍注明截至 2026-10-15，下方已有大量 10 月 16 日修订。虽非伪造状态，但读者需要扫描历史才能理解当前版本。
- 建议保留历史日志，在顶层维护一份简短现状表（本地实现、部署版本、真机验收）；专题正文只讲现行契约，历史行为移动到带日期的历史段落。顶部免责声明不能代替逐项修正错误的当前操作步骤。
